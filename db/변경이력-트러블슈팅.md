## 1. 최종 구조

```
categories (9행)  ──1:N──▶  category_rules (553행)
```

| 파일 | 역할 |
|---|---|
| `01_schema.sql` | 테이블 2개 생성 |
| `02_seed.sql` | 카테고리 9종 + 키워드 553개 + GIF 주소 |
| `03_access.sql` | RLS 및 조회 전용 권한 |
| `데이터흐름도.md` |  |
| `README-백엔드.md` | 백엔드 연동 가이드 |

DB는 분류 기준 데이터만 보관하고 런타임에는 읽기 전용이다.
분석 로직(정규화 · 자기이체 판별 · 카테고리 분류 · 이상치 판정 · 집계)은 전부 Backend가 수행한다.

## 2. 설계 변경 이력

하루 동안 네 차례 구조를 바꿨다. 각 단계마다 SQL 파일과 문서를 함께 수정하고,
로컬 PostgreSQL에서 전체 재실행으로 검증한 뒤 Supabase에 반영했다.

### 변경 요약

| 단계 | 테이블 | DB가 담당한 일 | 핵심 변화 |
|---|---|---|---|
| v1 | 4개 | 정규화·자기이체·분류·이상치·집계·JSON 조립 | 최초 설계 (기획서 기준) |
| v2 | 4개 | 정규화·자기이체·분류 | 이상치·집계를 Backend로 이관 |
| v3 | 3개 | 정규화·자기이체·분류 | 분석 세션 폐지, 사용자 이름 미저장 |
| v4 | **2개** | **없음** | **거래내역 미저장, DB는 기준 데이터만** |

### v1 — 최초 구현 (기획서 기준)

기획서의 ERD를 그대로 구현했다.

```
analysis_sessions ──1:N──▶ transactions ──N:1──▶ categories ──1:N──▶ category_rules
```

DB 안에 처리 로직을 전부 넣었다.

- 함수 : `normalize_text()` `mark_self_transfers()` `classify_transactions()` `process_analysis()`
- 뷰 : `v_transaction_detail` `v_category_summary` `v_representative_category`
- RPC : `get_analysis_result()` — 프론트에 내려줄 JSON을 통째로 반환

백엔드는 거래를 저장하고 함수 하나를 호출한 뒤 JSON을 그대로 전달하기만 하면 되는 구조였다.

### v2 — 이상치 판정과 집계를 Backend로 이관

**변경 배경**

DB가 계산까지 전담하면 백엔드가 실제로 구현할 로직이 없어진다.
저장·조회·전달만 남아 역할 분담(R&R)이 한쪽으로 치우친다.

**결정**

저장되는 값과 계산되는 값의 담당을 계층으로 나눴다.

| 처리 | 담당 | 근거 |
|---|---|---|
| 자기이체 판별 · 카테고리 분류 | DB | 결과를 테이블에 **저장**해야 하고, 키워드 553건이 DB에 있음 |
| 이상치 판정 · 합계 · 비율 · 대표 카테고리 | Backend | **저장하지 않는** 계산값 |

**영향**

- `03_logic.sql` — 뷰 3개, `get_analysis_result()` 제거
- `04_access.sql` — 뷰·RPC 권한 구문 제거, `DROP VIEW` 추가
- `05_sample_test.sql` — 집계 쿼리를 "백엔드 대조용 정답지"로 용도 변경
- ERD 변경 없음 (이관 대상이 전부 저장되지 않는 계산값이었음)

**확인 사항** — 뷰가 내주던 숫자와 이관 후 숫자가 동일함을 로컬에서 확인했다.
FOOD 118,000원(81.0%) / LIVING 26,430원(18.1%) / OTHER 1,250원(0.9%)

### v3 — 분석 세션 폐지, 사용자 이름 미저장

**변경 배경**

`analysis_sessions.user_name` 은 자기이체를 판별하는 순간에만 사용되고
그 이후 어디에서도 다시 읽히지 않는다. 저장할 이유가 없다.

**검토한 쟁점**

`analysis_sessions` 는 두 가지 일을 하고 있었다.

1. `user_name` 보관 → 불필요
2. 거래들을 한 번의 분석 단위로 묶기 → 필요 여부를 따로 판단해야 함

②에 대해서는 "한 번의 분석이 끝나면 새로운 분석이 있을 뿐"이라는 서비스 성격상
분석 단위를 식별할 필요가 없다고 판단했다. 직전 분석을 대체하는 단일 분석 모델로 정했다.

**결정**

- `analysis_sessions` 테이블 폐지
- `transactions.analysis_id` 제거
- `user_name` 은 `process_analysis(user_name)` 파라미터로만 전달, 저장하지 않음
- `start_analysis()` 추가 — 새 분석 시작 시 이전 거래를 비우고 ID를 1부터 재시작

**영향**

- API 응답에서 `analysis_id`, `user_name` 제거 → 프론트가 입력한 이름을 화면에 보관
- `GET /api/analyses/{id}` → `GET /api/analyses/current` 로 변경
- 백엔드 Entity 1개 삭제

**확인 사항** — 2회 연속 분석을 시뮬레이션해 이전 12건이 지워지고 ID가 1부터 다시 시작하는 것을 확인했다.

**알려진 제약** — 동시에 두 명이 분석하면 서로의 데이터를 덮어쓴다. 시연은 한 번에 한 명씩 진행한다.

### v4 — 거래내역 미저장, DB는 기준 데이터만 (최종)

**변경 배경**

은행 거래내역은 민감한 개인 금융정보다. 분석이 끝나면 재사용하지 않는 데이터를
서버에 남길 이유가 없다.

**결정**

- `transactions` 테이블 폐지
- DB 함수 전부 제거 — DB는 판단하지 않는다
- 분석 로직 전체를 Backend로 이관 (정규화 · 자기이체 · 분류 · 이상치 · 집계 · 대표 카테고리)
- DB에는 분류 기준만 보관 : 카테고리 9종, 이상치 기준 금액, 키워드 553개, GIF 주소

| DB에 저장 | 저장하지 않음 |
|---|---|
| 카테고리 · 이상치 기준 금액 | 사용자 이름 |
| 분류 키워드 · GIF 주소 | 거래 상대 · 거래 금액 |
| | 분류 결과 · 이상치 판정 · 집계 결과 |

**`category_rules` 를 DB에 남긴 이유**

키워드 553건과 카테고리별 기준 금액은 운영 중 계속 조정될 값이다.
DB에 두면 코드 배포 없이 수정할 수 있고, 카테고리와 키워드의 1:N 관계를 정규화해
기준 금액을 한 곳에서만 관리할 수 있다. 코드에 상수로 넣으면 두 이점을 모두 잃는다.

**영향**

- 파일 구성 변경 : `03_logic.sql` 삭제, `04_access.sql` → `03_access.sql`, `05_sample_test.sql` → `04_verify.sql`
- API가 `POST /api/analyses` 하나로 축소, 응답 코드 `201` → `200`
  (서버에 생성되는 리소스가 없으므로)
- 백엔드가 앱 시작 시 두 테이블을 읽어 캐싱하는 구조로 변경
- `README-백엔드.md` 전면 재작성 — 백엔드가 구현할 분석 로직 전체를 코드로 제공

**채점 대응**

테이블이 2개로 줄면서 "엔티티·관계·정규화" 채점 근거가 얇아질 수 있다고 판단했다.
이를 보완하기 위해 다음을 문서에 명시했다.

- 정규화 근거 : `FOOD` 와 기준금액 30000이 201번 반복 저장되는 문제를 1:N 분리로 해결
- trace-through : 화면의 각 항목이 어디서 오는지, DB 저장 여부를 표로 정리
- 저장하지 않는 항목마다 그 이유를 명시

## 3. 트러블슈팅

### 3-1. Supabase 뷰가 RLS를 우회함

**증상** — 테이블에 RLS를 걸어 `anon` 키 접근을 막았는데, 뷰를 통하면 전체 데이터가 조회됐다.

**원인** — PostgreSQL 뷰는 기본적으로 **뷰 소유자 권한**으로 실행된다.
뷰를 만든 계정이 `postgres` 이므로, 뷰를 호출한 사람의 RLS 정책이 적용되지 않는다.

**해결** — 뷰 정의에 `security_invoker` 옵션을 추가했다.

```sql
CREATE OR REPLACE VIEW v_transaction_detail
WITH (security_invoker = on) AS
...
```

이 옵션을 켜면 뷰를 **호출한 역할**의 권한으로 실행되어 기반 테이블의 RLS가 그대로 적용된다.

> v4에서 뷰를 모두 제거해 현재는 해당 사항 없음. 다만 Supabase에서 뷰를 쓸 때는 항상 확인해야 한다.

---

### 3-2. DBML `check` 문법이 동작하지 않음

**증상** — `dutch_threshold int [not null, check: \`dutch_threshold > 0\`]` 작성 시 파싱 실패.

```
Expected "default:", "increment", "not null", "note:", "null",
"pk", "primary key", "ref:", "unique" ... but "c" found.
```

**원인** — **DBML은 `check` 를 지원하지 않는다.**
가이드 문서(`how2table_ERD_DBML.pdf`) 5-3절 문법표와 5-2절 예시 코드에 `[check: ...]` 가
포함되어 있으나, 실제 DBML 파서와 dbdiagram.io는 이 문법을 받지 않는다.

**해결** — CHECK 제약은 `CREATE TABLE`(`01_schema.sql`)에만 두고, DBML에는 주석으로 남겼다.

```dbml
dutch_threshold int [not null]   // 이상치 판정 기준 금액(CHECK: 0보다 커야 함)
```

**조 공유 사항** — 가이드 예시를 그대로 따라 쓰면 다른 조도 같은 곳에서 막힌다.

---

### 3-3. Supabase 실행 시 경고창

**증상** — SQL 실행 시 `Potential issues detected` 경고가 떠서 실패로 오인했다.

```
This query includes destructive operations.
This query creates tables without enabling Row Level Security.
```

**원인** — 에러가 아니라 확인 절차다.

- 첫 번째 : `01_schema.sql` 상단의 `DROP TABLE IF EXISTS` 때문 (멱등성 확보용)
- 두 번째 : RLS는 `03_access.sql` 에서 설정하므로 이 시점에는 아직 꺼져 있음

**해결** — RLS 체크박스를 켜고 실행 버튼을 눌렀다. `Success. No rows returned` 는
"테이블 생성처럼 반환할 데이터가 없는 명령"이라는 뜻으로 정상이다.

---

### 3-4. `created_at` 시각이 9시간 어긋나 보임

**증상** — 11시 26분에 넣은 데이터의 `created_at` 이 `02:26:28` 로 표시됐다.

**원인** — `TIMESTAMPTZ` 는 시간을 UTC 기준으로 저장하고, Supabase Table Editor도 UTC로 표시한다.
한국시간(KST)은 UTC+9 이므로 9시간 차이가 난다. **데이터는 정확하다.**

**해결** — 조회 시 변환한다. DB에 한국시간을 직접 저장하는 방식은 서버 위치가 바뀌면
문제가 생기므로 채택하지 않았다.

```sql
SELECT created_at AT TIME ZONE 'Asia/Seoul' FROM ...;
```

> v3에서 `analysis_sessions` 를 폐지하며 해당 컬럼도 함께 제거되어 현재는 해당 사항 없음.

---

### 3-5. GIF 파일명에 공백 포함

**증상** — `HEALTH .gif` 파일명에 공백이 들어 있어 `gif_url` 과 경로가 맞지 않았다.

**해결** — `HEALTH.gif` 로 수정. 9개 파일명을 `category_name` 과 정확히 일치시켰다.

이 규칙 덕분에 URL 갱신을 문자열 결합 한 줄로 처리할 수 있다.

---

### 3-6. Supabase 접속 정보 위치

**증상** — Project Settings 안에서 연결 문자열을 찾지 못했다.

**해결** — 상단 초록색 `Connect` 버튼에 있다.

```
Connect → [Direct] Connection string 카드
        → 탭에서 [Session pooler] 선택
        → 형식 [JDBC] 선택
```

`Direct` 카드는 "라이브러리 없이 DB에 직접 붙는 방법 모음"이라는 뜻이고,
그 안에 Session pooler도 들어 있다. 카드 이름과 탭 이름이 겹쳐 헷갈리기 쉽다.

---

### 3-7. 백엔드 연결 실패 예방 조치

실제로 겪지는 않았지만 발생 가능성이 높아 문서에 미리 반영한 항목들이다.

| 항목 | 내용 |
|---|---|
| **Direct connection 사용 금지** | `db.xxx.supabase.co` 는 IPv6 전용이라 일반 인터넷망에서 연결되지 않는다. 반드시 Session pooler(`pooler.supabase.com:5432`)를 쓴다 |
| **사용자명 형식** | Session pooler는 `postgres` 가 아니라 `postgres.<프로젝트ID>` 다 |
| **`ddl-auto: validate` 고정** | `update` 로 두면 Hibernate가 테이블 구조를 바꾸거나 시드 데이터를 날릴 수 있다 |
| **JSON 필드명** | `spring.jackson.property-naming-strategy: SNAKE_CASE` 로 DB 컬럼명과 일치시킨다 |
| **키워드 정렬** | 길이 내림차순으로 정렬하지 않으면 `쿠팡이츠` 가 `쿠팡`(SHOPPING)에 먼저 걸린다 |

## 4. 작업 방식

### 로컬 사전 검증

Supabase에 바로 실행하지 않고, 로컬 PostgreSQL 17에 테스트 DB를 만들어 전체 SQL을
처음부터 실행해 본 뒤 반영했다. Supabase는 되돌리기가 번거롭기 때문이다.

```
빈 DB 생성 → 01 → 02 → 03 → 04 순서대로 실행 → 오류 및 결과 확인 → Supabase 반영
```

구조를 바꿀 때마다 이 과정을 반복했다. 덕분에 Supabase에서는 문법 오류가 한 번도 발생하지 않았다.

### 멱등성 확보

`01_schema.sql` 상단에 `DROP TABLE IF EXISTS` 를, `03_access.sql` 상단에 구버전 객체
정리 구문을 넣어 **몇 번을 실행해도 같은 상태가 되도록** 했다.
네 차례 구조를 바꾸는 동안 이전 버전의 테이블·함수·뷰가 남지 않고 자동으로 정리됐다.

### 검증 정답지 유지

분석 로직이 Backend로 옮겨가면서, 백엔드 계산 결과를 검증할 기준이 필요해졌다.
`04_verify.sql` §3~§5 에 실제 거래내역 캡처 12건에 대한 기대값을 SQL로 작성해두고
백엔드 응답과 대조할 수 있게 했다.

```
FOOD    118,000원  5건  81.0%   ← 대표 카테고리 → FOOD.gif
LIVING   26,430원  4건  18.1%
OTHER     1,250원  2건   0.9%
total_spent = 145,680원

이상치 후보 : 고기굽는남자 하남점  88,000원 > FOOD 기준 30,000원
자기이체    : 김 지 영  50,000원 → 0원 처리, 결과에서 제외
```

## 5. 팀 공유 및 후속 조치

| 항목 | 대상 | 상태 |
|---|---|---|
| DB 접속 정보 전달 (5개 값 + 비밀번호) | 백엔드 | 진행 |
| `README-백엔드.md` 최신본 전달 | 백엔드 | 진행 — v4로 전면 개정됨, 이전 버전 폐기 필요 |
| 응답에서 `analysis_id`·`user_name` 제거 | 프론트 | 공유 필요 |
| 기획서 ERD·Entity 표 교체 (4테이블 → 2테이블) | 설계문서 담당 | 수정본 작성 완료 |
| API 명세 `POST /api/analyses` 단일 | API 담당 | 공유 필요 |

### 기준 데이터 변경 요청 절차

카테고리 키워드, 이상치 기준 금액, 카테고리 추가는 DB 변경 사항이므로 DA를 통해 처리한다.
대시보드에서 직접 수정하면 SQL 파일과 실제 DB가 어긋나 재구축 시 문제가 생긴다.

백엔드는 앱 시작 시 기준 데이터를 캐싱하므로, **변경 후에는 백엔드 재시작이 필요하다.**
