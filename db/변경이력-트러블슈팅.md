### v2 — 이상치 판정과 집계를 Backend로 이관

**변경 배경**

비즈니스 로직의 DB 의존도를 낮추고, 기능 확장과 유지보수가 쉬운 구조로 개선하기 위해 계산·분석 로직을 백엔드로 이관했다.

**결정**

저장되는 값과 계산되는 값의 담당을 계층으로 나눴다.

| 처리 | 담당 | 근거 |
|---|---|---|
| 자기이체 판별 · 카테고리 분류 | DB | 결과를 테이블에 저장해야 하고, 키워드 553건이 DB에 있음 |
| 이상치 판정 · 합계 · 비율 · 대표 카테고리 | Backend | 저장하지 않는 계산값 |

**영향**

- `03_logic.sql` — 뷰 3개, `get_analysis_result()` 제거
- `04_access.sql` — 뷰·RPC 권한 구문 제거, `DROP VIEW` 추가
- `05_sample_test.sql` — 집계 쿼리를 "백엔드 대조용 정답지"로 용도 변경
- ERD 변경 없음 (이관 대상이 전부 저장되지 않는 계산값이었음)

### v3 — 분석 세션 폐지, 사용자 이름 미저장

**변경 배경**

`analysis_sessions.user_name` 은 자기이체를 판별하는 순간에만 사용되고
그 이후 어디에서도 다시 읽히지 않는다. 저장할 이유가 없다.

**검토한 쟁점**

`analysis_sessions` 는 두 가지 일을 하고 있었다.

1. `user_name` 보관 → 불필요
2. 거래들을 한 번의 분석 단위로 묶기 → 필요 여부를 따로 판단해야 함

②에 대해서는 "한 번의 분석이 끝나면 새로운 분석이 있을 뿐"이라는 서비스 성격상
분석 단위를 식별할 필요가 없다고 판단했다. 직전 분석을 대체하는 단일 분석 모델로 정했다.

**결정**

- `analysis_sessions` 테이블 폐지
- `transactions.analysis_id` 제거
- `user_name` 은 `process_analysis(user_name)` 파라미터로만 전달, 저장하지 않음
- `start_analysis()` 추가 — 새 분석 시작 시 이전 거래를 비우고 ID를 1부터 재시작

**영향**

- API 응답에서 `analysis_id`, `user_name` 제거

### v4 — 거래내역 미저장, DB는 기준 데이터만 (최종)

**변경 배경**

거래내역을 서버에 저장하지 않고 분석 요청 시점에만 처리하는 구조로 변경해, 데이터 보관에 따른 보안 부담을 줄였다.

**결정**

- `transactions` 테이블 폐지
- DB 함수 전부 제거 — DB는 판단하지 않는다
- 분석 로직 전체를 Backend로 이관 (정규화 · 자기이체 · 분류 · 이상치 · 집계 · 대표 카테고리)
- DB에는 분류 기준만 보관 : 카테고리 9종, 이상치 기준 금액, 키워드 553개, GIF 주소

| DB에 저장 | 저장하지 않음 |
|---|---|
| 카테고리 · 이상치 기준 금액 | 사용자 이름 |
| 분류 키워드 · GIF 주소 | 거래 상대 · 거래 금액 |
| | 분류 결과 · 이상치 판정 · 집계 결과 |

**`category_rules` 를 DB에 남긴 이유**

키워드 553건과 카테고리별 기준 금액은 운영 중 계속 조정될 값이다.
DB에 두면 코드 배포 없이 수정할 수 있고, 카테고리와 키워드의 1:N 관계를 정규화해 기준 금액을 한 곳에서만 관리할 수 있다.

**영향**

- 파일 구성 변경 : `03_logic.sql` 삭제, `04_access.sql` → `03_access.sql`, `05_sample_test.sql` → `04_verify.sql`

## 3. 트러블슈팅

### 3-1. Supabase 뷰가 RLS를 우회함

**증상** — 테이블에 RLS를 걸어 `anon` 키 접근을 막았는데, 뷰를 통하면 전체 데이터가 조회됐다.

**원인** — PostgreSQL 뷰는 기본적으로 **뷰 소유자 권한**으로 실행된다.
뷰를 만든 계정이 `postgres` 이므로, 뷰를 호출한 사람의 RLS 정책이 적용되지 않는다.

**해결** — 뷰 정의에 `security_invoker` 옵션을 추가했다.

```sql
CREATE OR REPLACE VIEW v_transaction_detail
WITH (security_invoker = on) AS
...
```

이 옵션을 켜면 뷰를 **호출한 역할**의 권한으로 실행되어 기반 테이블의 RLS가 그대로 적용된다.

> v4에서 뷰를 모두 제거해 현재는 해당 사항 없음. 다만 Supabase에서 뷰를 쓸 때는 항상 확인해야 한다.

---

### 3-2. DBML `check` 문법이 동작하지 않음

**증상** — `dutch_threshold int [not null, check: \`dutch_threshold > 0\`]` 작성 시 파싱 실패.

```
Expected "default:", "increment", "not null", "note:", "null",
"pk", "primary key", "ref:", "unique" ... but "c" found.
```

**원인** — **DBML은 `check` 를 지원하지 않는다.**
가이드 문서(`how2table_ERD_DBML.pdf`) 5-3절 문법표와 5-2절 예시 코드에 `[check: ...]` 가
포함되어 있으나, 실제 DBML 파서와 dbdiagram.io는 이 문법을 받지 않는다.

**해결** — CHECK 제약은 `CREATE TABLE`(`01_schema.sql`)에만 두고, DBML에는 주석으로 남겼다.

```dbml
dutch_threshold int [not null]   // 이상치 판정 기준 금액(CHECK: 0보다 커야 함)
```
